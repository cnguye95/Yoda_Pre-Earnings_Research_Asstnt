3. Incorporate 8-K filings and post-filing developments ("Option 2 + tool")
   Goal: the 10-Q/10-K is ground truth for its period but is already stale on
   release. Add the layers analysts use to see what changed since, keeping
   every claim labelled by source, as-of date and evidence type — never
   letting news overwrite filing numbers.

3.1 Ingest 8-Ks filed after the primary 10-Q/10-K (yoda/ingest/edgar.py)
   - Fetch 8-Ks with filing_date > primary filing_date (SEC submissions JSON
     already lists them; same _sec_get + cache path).
   - Read the Item codes to know what each 8-K is: 2.02 = earnings release
     (Exhibit 99.1 press release — often out days/weeks BEFORE the 10-Q),
     1.01 = material agreement, 2.01 = acquisition/disposal, 2.03 = new debt,
     5.02 = executive change, 7.01/8.01 = Reg FD / other events.
   - Model: a Filing-like record per 8-K (date, items, exhibit text, url).
   - Embed into ChromaStore so personalities can retrieve it.

3.2 Evidence types — tag every claim
   reported     = company actuals for a closed period (10-Q/10-K, 8-K 2.02 release)
   guided       = management's own outlook (release, call, 8-K 7.01)
   estimate     = third-party expectation (consensus, analyst targets, whisper)
   proxy        = indirect signal (alt data, peer read-through, industry stats)
   unverifiable = claim lacks evidence to be tagged reported, guided, estimate, or proxy
   - Add evidence_type + as_of_date + source to Hypothesis evidence quotes and
     to a new report section (see 3.5).
   - News articles are tagged by the ORIGINAL source the article names for
     the claim, not as "news". The personality may tag the claim when the
     article attributes it, e.g.:
       "Netflix reported revenue of $X in its Q2 filing"  -> reported
       "management expects Q3 margins of Y%"               -> guided
       "analysts polled by LSEG expect EPS of $Z"          -> estimate
       "card-spending data from <firm> shows sales down"   -> proxy
     The attributed source is recorded alongside the tag.
     * News article source should also be tagged (e.g. marketbeat, SeekingAlpha).
   - Edge case: if the article does not say where the claim comes from, the
     claim is tagged "unverifiable".

3.3 New personality tool: search_developments(query)
   - Searches post-filing 8-Ks + news + consensus.py data; every result comes
     back pre-tagged with evidence_type, as_of_date and source.
   - Wire consensus.py into this tool and into synthesis.

3.4 Weigh claims — two dimensions: reliability and relevance (AGREED DESIGN)
   - Recommendation (agreed):
     * Reliability: categorical tag (reported > guided > estimate > proxy).
       Assigned in code wherever the source type is known (SEC filings,
       consensus feed). For news articles the personality assigns it from
       the source the article names, and code checks the tag fits that
       stated source (3.2); no stated source -> "unverifiable".
     * Relevance: coarse category judged by the personality per hypothesis
       — "direct" (same metric/period as the question) vs "context" — with a
       one-line reason, which the critique step can challenge.
     * No numeric weights at first. Rules instead: a hypothesis needs at
       least one direct claim; proxy-only hypotheses are capped at 3/5;
       on conflicts for the same metric/period, the more reliable tier wins
       and both are shown.
     * Revisit numeric weighting only if the eval shows the categorical
       rules aren't enough.

3.5 Report schema (yoda/schema.py)
   - key_metrics stays filing-only ("reported", with the period it covers).
   - New section, e.g. since_filing: list of {claim, evidence_type,
     as_of_date, source, url} — 8-K events, guidance, consensus, proxies.
   - New section, e.g. market_expectations: consensus EPS/revenue, whisper,
     implied move (from consensus.py), each with source + as-of.
   - Every Metric gains a period/as-of field so staleness is visible.

3.6 Synthesis prompt rules (yoda/modes/personality_panel.py _SYNTHESIS_SYSTEM)
   - Rule 1: keep "FILING TEXT is the only source for key_metrics,
     revenue_segments and their citations" (reported history). Amend to say
     post-filing information goes in since_filing / market_expectations with
     its evidence_type — never into key_metrics, never overwriting a filing
     number. An 8-K 2.02 press release counts as a reported source for its
     own period and may be cited like a filing.
   - Rule 5: DONE (commit 709ae6e) — retired the conflicting first sentence
     ("not supported by hypothesis evidence or news -> data_gaps"), which
     contradicted rule 1 (a figure in the filing is supported even if no
     personality looked at it). KEEP its data_gaps definition — "only facts
     the filing/8-Ks/news SHOULD have covered but did not; forward-looking
     items like consensus are NOT gaps" — moved into its own data_gaps rule.
     Without it, the model fills data_gaps with "Q3 consensus not in
     filing"-style noise.
   - New rule: label every since_filing claim with its evidence_type and
     as-of date; when tiers conflict on the same metric/period, state both
     and say which is more reliable.
   - Citations: allow "8-K Item 2.02, Exhibit 99.1 — <heading>" format.
   - Update baseline prompt too, or the eval comparison is no longer fair
     (see 4 for what the baseline is given).
   - REMEMBER TO UPDATE RULE 1 AND 5 TO MAKE SURE THEY ARE CONSISTENT WITH
     NEW 8-K FEATURE.
     * Rule 1’s “only known from external sources → data_gaps” overlaps with
       rule 5’s “external items are NOT gaps”. Rule 5’s “SHOULD have covered”
       test mostly settles it. The real fix is the “since filing” section in
       the 8-K work, which gives external facts their own home, so I left
       the wording alone for now.

3.7 Eval
   - Judge rubric: add a dimension (or criterion under accuracy) for
     "post-filing information is labelled and not mixed into reported figures".
     AGREED: judged tag-agnostic — for each post-filing claim, can a reader
     tell where it came from, as of when, and whether it is a reported
     result, management outlook or third-party estimate? Plain wording
     ("the Street expects", "per the 8-K", "according to Reuters") scores
     the same as an evidence_type tag. Tag correctness is checked by 3.10's
     tests, not by the judge.
   - Evidence cache for the judge (eval runs only): every mode returns its
     evidence bundle on every run (already in memory, no extra cost); only
     the eval runner writes it to disk, next to the report JSON. The judge
     reads that bundle, so it sees what the report saw.
     * Contents: external sources only — filings, 8-Ks, news results,
       consensus.py data, transcript chunks. Each item carries its own
       citation (source, URL or accession number, as-of date) so the
       report's citations can be matched to it.
     * News: full article text only for articles the report cites; every
       other news-pool item as its snippet. Keeps the judge's prompt small
       and free of text the report never relied on.
     * Never Yoda's own hypotheses or critique messages: they are Yoda's
       reasoning, not sources, and would let a claim be "verified" by Yoda
       quoting itself. (They get their own grading in 5.)
   - Re-run baseline vs Yoda after; expect cost/latency increase — measure it.

3.8 Earnings press release + call transcript as context
   - Press release: on EDGAR as 8-K Item 2.02, Exhibit 99.1 — free, covered
     by 3.1. Usually the first "reported" numbers for the quarter and the
     main source of quarterly guidance.
   - Call transcript: NOT on EDGAR. Needs a vendor (FMP/Finnhub transcript
     endpoints — check plan cost and terms). Valuable for guidance wording
     and analyst Q&A; long, so retrieve chunks rather than send in full.

3.9 Personality "analyst playbook" + source vetting (current gap)
   - Today the personality prompts give a lens (3-5 sentences) and tool
     rules, but nothing on what moves a stock on earnings (results vs
     consensus, guidance changes, key KPIs, margins), what news to look
     for, or how to judge a source. The models have general financial
     knowledge but are not told to apply it.
   - Code does no source vetting: search_news (Tavily) has no news-topic,
     date-range or domain filter; the URL-pool check only proves a URL came
     from a search, not that the source is credible.
   - Add: a shared playbook section in _BASE_LOOP_CONTRACT; a source-tier
     list (company primary > data vendors > major financial press >
     aggregators/blogs); Tavily topic="news" + a time window starting at the
     filing date; tag-vs-source validation — a tag must match the source
     the article attributes the claim to (see 3.2); a claim with no
     stated source is tagged "unverifiable".
   - Full-article reading (AGREED; cost accepted for now, may cut later).
     Personalities see Tavily snippets cut to 300 characters, which often
     drops the sentence saying where a claim came from — the attribution
     3.2's tagging depends on.
     * Add a read_article(url) tool (Tavily Extract) returning the cleaned
       article, capped at ~5K tokens (AGREED). A typical extracted article
       is ~2-3K tokens, so ~90% come through whole; the cap only cuts long
       pages such as transcripts posted as articles (15-20K tokens). Only
       URLs already in the news pool are accepted, so the URL-pool check
       still holds. Personalities call it only for articles they want to
       rely on.
     * Estimated +$0.08 per ticker, not yet measured: ~9 reads per run,
       ~3K tokens each on average (Haiku ~$0.01; Tavily Extract ~2 credits
       = ~$0.016 once past the free 1,000 credits/month; synthesis ~$0.05
       if it gets the read articles). Judge: ~+$0.06 per report (cited
       articles only, 3.7). Measure on the first 1-ticker run.
     * Rejected: no cap — ~$0.12 per run typical but ~$0.25-0.30 when long
       pages push a Haiku prompt past 100K tokens (5x price), and can push
       JPM's judge call past 272K tokens (2x price for the whole call).
     * Each read uses one of MAX_TOOL_CALLS (6) and adds seconds against
       WALL_TIMEOUT_SECONDS (45s); raise them if reads crowd out other tools.
     * Rejected: full text on every search result (include_raw_content) —
       est. +$0.25-0.55 per run, pushes Haiku prompts past 100K tokens
       (5x price) and floods synthesis and the judge with articles no one
       cited.

4. Eval baseline: replace the filing-only baseline (AGREED: option B now,
   option C later)
   The baseline is the simplest credible alternative to Yoda; what it is
   given decides what a Yoda win proves.

   Option B — NEW BASELINE: one Claude call, given what an analyst would
   have on hand:
   - SEC filings: the 10-Q/10-K (+ supplemental 10-K) and every 8-K filed
     after it, incl. the Exhibit 99.1 press release (3.1 and 3.8).
   - Market data from consensus.py (consensus EPS/revenue, whisper,
     implied move). Ideally fetched once per ticker and shared with Yoda,
     so both modes see identical numbers.
   - ONE fixed, generic news search (e.g. "<TICKER> earnings", same Tavily
     settings as Yoda) — not the queries Yoda's personalities choose.
   - Question it answers: "Does Yoda's multi-agent panel write a better
     pre-earnings brief than a single model call given the same kinds of
     information an analyst has on hand (SEC filings, market data, a
     generic news search)?" A Yoda win then points to Yoda's method (its
     research choices and multiple perspectives), not to extra data.
   - HARD GUARDRAIL — Yoda's research must never leak into the baseline:
     * The baseline's inputs come from one builder function that can only
       read SEC filings, the market data and its own generic search. It
       never takes Yoda's news_pool, hypotheses, critique messages, report
       JSON or evidence bundle.
     * Running the baseline first (the runner already does, per ticker) is
       not enough on its own: Yoda's files from an earlier ticker or run
       are still on disk, and a baseline-only run can happen after Yoda.
     * Offline test: plant a marker string in a fake Yoda report, news pool
       and evidence bundle on disk, build the baseline prompt, and assert
       the marker never appears in it.
   - The baseline's evidence goes into the same eval evidence cache as
     Yoda's (3.7).
   - Prompt asks for the since_filing section but NOT Yoda's tagging rules
     (an analyst wouldn't run an equivalent tagging system). It still sees
     the tag names in the shared report schema and fills them by judgement;
     the judge scores labelling tag-agnostic (3.7).

   Option C — ADD LATER as a second baseline: the SEC filings above plus
   Claude's web search tool.
   - Question it answers: "Does Yoda beat an analyst using a general AI
     assistant with web search (e.g. Google AI Mode, ChatGPT search)?" —
     likely the most common way analysts do quick research today.
   - Results vary run to run, it costs more, and it is a small agent rather
     than one call; every search it runs must be saved to the eval
     evidence cache so the judge sees what it saw.


5. Yoda-only process check (LATER, separate from Yoda vs baseline)
   The head-to-head eval grades only the final report, so hypotheses and
   critique are kept out of it (3.7). They are still worth grading on
   their own, to find out whether Yoda's extra steps earn their cost:
   - Does each personality add something the others don't?
   - Does the critique catch real errors (CHALLENGES that were right)?
   - Does synthesis carry well-supported findings into the report
     faithfully — not dropping them, not inventing new ones?
   - Never mixed into the Yoda-vs-baseline scores: the baseline has no
     process to grade, and showing the judge Yoda's working would tilt
     the comparison toward Yoda.
