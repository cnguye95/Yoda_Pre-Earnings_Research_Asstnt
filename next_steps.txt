2. Eval baseline: replace the filing-only baseline (AGREED: option B now,
   option C later)
   The baseline is the simplest credible alternative to Yoda; what it is
   given decides what a Yoda win proves.
   - Until this is built, several new dimensions are unfair to the
     filing-only baseline (8-K part of filing_extraction,
     market_expectations, evidence_labelling, both usefulness scores).
     They are addressed together with this baseline; no eval runs before
     then (AGREED).
   - Update the baseline prompt (yoda/modes/baseline.py) for the new report
     sections, or the comparison is no longer fair.
   - FOUND (schema step): the baseline fills panel-only fields it was never
     meant to. 8 of the 20 archived baseline reports (AMD, AMZN, CRM, DIS,
     JPM, PANW, PG, UNH) contain hypotheses_explored with invented analysts
     ("Growth analyst", confidence 65-80); baseline.py strips recent_news
     but not this. Today's stricter Hypothesis rules would reject such a
     reply and fail the run. When this baseline is built, strip
     hypotheses_explored, and decide how it fills since_filing and
     market_expectations (it shares the report schema).

   Option B — NEW BASELINE: one Claude call, given what an analyst would
   have on hand:
   - SEC filings: the 10-Q/10-K (+ supplemental 10-K) and every 8-K filed
     after it, incl. the Exhibit 99.1 press release.
   - Market data from consensus.py (consensus EPS/revenue, whisper,
     implied move). Ideally fetched once per ticker and shared with Yoda,
     so both modes see identical numbers.
   - Analyst rating actions from the last 30 days, LISTED ONE BY ONE
     (firm, previous rating -> new rating, date; from FMP grades, the same
     list Yoda's market_expectations.analyst_actions shows). Counts alone
     are not enough: the baseline must see which firm changed what.
   - ONE fixed, generic news search (e.g. "<TICKER> earnings", same Tavily
     settings as Yoda) — not the queries Yoda's personalities choose.
   - Question it answers: "Does Yoda's multi-agent panel write a better
     pre-earnings brief than a single model call given the same kinds of
     information an analyst has on hand (SEC filings, market data, a
     generic news search)?" A Yoda win then points to Yoda's method (its
     research choices and multiple perspectives), not to extra data.
   - HARD GUARDRAIL — Yoda's research must never leak into the baseline:
     * The baseline's inputs come from one builder function that can only
       read SEC filings, the market data and its own generic search. It
       never takes Yoda's news_pool, hypotheses, critique messages, report
       JSON or evidence bundle.
     * Running the baseline first (the runner already does, per ticker) is
       not enough on its own: Yoda's files from an earlier ticker or run
       are still on disk, and a baseline-only run can happen after Yoda.
     * Offline test: plant a marker string in a fake Yoda report, news pool
       and evidence bundle on disk, build the baseline prompt, and assert
       the marker never appears in it.
   - The baseline's evidence goes into the same eval evidence cache as
     Yoda's, so the judge sees what the baseline saw.
   - Prompt asks for the since_filing section but NOT Yoda's tagging rules
     (an analyst wouldn't run an equivalent tagging system). It still sees
     the tag names in the shared report schema and fills them by judgement;
     the judge scores labelling tag-agnostic.

   Option C — ADD LATER as a second baseline: the SEC filings above plus
   Claude's web search tool.
   - Question it answers: "Does Yoda beat an analyst using a general AI
     assistant with web search (e.g. Google AI Mode, ChatGPT search)?" —
     likely the most common way analysts do quick research today.
   - Results vary run to run, it costs more, and it is a small agent rather
     than one call; every search it runs must be saved to the eval
     evidence cache so the judge sees what it saw.

   FINDINGS (2026-10-30, offline check of the 26 cached tickers' filings)
   - The bigger problem is section LABELS, not chunk splitting. The
     chunker's section detector mislabels most filings, not just JPM:
     * In most 10-Ks "Quantitative Disclosures" (Item 7A, usually about a
       page) covers 30-50% of the text (AMZN 50%, CAT 49%, JNJ 54%), while
       MD&A gets 2-3% (CAT, KO, MSFT, JPM). In 10-Qs, "Risk Factors" often
       takes 30-60% (AMD 63%, FTNT 59%) and "Other" up to 81% (JPM).
     * Cause 1: a heading is ANY short line that contains a section
       phrase, so a footnote ("(c) ... on the Consolidated balance
       sheets"), a bullet ("• ... Item 1A: Risk Factors in ..."), a
       running page header ("Management's discussion and analysis") or a
       glossary entry counts as a heading.
     * Cause 2: "keep the last occurrence of each label" assumes the table
       of contents comes first and the body heading last. Cross-references,
       footnotes and glossaries after the body break that, so the chosen
       "heading" is often near the end of the filing.
     * Cause 3: only five sections are detected, so a section runs until
       the next detected heading: Item 7A swallows Item 8 and the notes,
       because "Item 8. Financial Statements" is not one of the patterns.
     * Cause 4: some 10-Ks are a short wrapper around an annual report
       (JPM's cross-reference index; USB incorporates its Annual Report,
       Exhibit 13, which Yoda does not read at all: its "10-K" is 138K
       characters with no MD&A or financial statements).
   - Where it matters today:
     * Every filing citation carries the label ("10-K · Risk Factors —
       ..."), so readers (and the judge) see the wrong Item named.
     * The size rule trims an older 10-K by label (Financial Statements,
       then Quantitative Disclosures, then MD&A), so it can cut MD&A text
       labelled as 7A. This only affects JPM-size filings (see below).
     * Retrieval itself ignores labels: chunks are found by embedding
       similarity alone (text-embedding-3-small, top 3 per filing).

   RECOMMENDATIONS (in order; each needs its own approval)
   R1. Build a small section test set first (offline, free): for ~8
       cached filings (one each of a normal 10-K, normal 10-Q, JPM 10-K,
       USB 10-K, 20-F, 40-F) record where Items 1, 1A, 7, 7A and 8 really
       start. Assert each approach against it.
       + Turns "looks wrong" into a number; every later change is checked.
       - An hour of manual reading; covers only the filings chosen.
   R2. Fix section detection. Options, simplest first:
       a. Stricter in-house rules: only a line that STARTS with
          "Item N." (optionally "Part I,") is a heading; every Item
          heading is a boundary (Items Yoda doesn't name become "Other");
          skip the table of contents by ignoring an Item heading that is
          followed by another Item heading within a few hundred
          characters.
          + Small change, no new dependency, easy to test.
          - Still hand-rolled parsing (CLAUDE.md prefers a tested
            library); does nothing for wrapper filings (JPM, USB) or
            20-F/40-F, which use different Item numbers or none.
       b. A maintained library: edgartools (pip "edgartools") parses
          10-K / 10-Q / 20-F filings into Items. RECOMMENDED to try first.
          + Follows CLAUDE.md's order (library before hand-rolled); it is
            tested on far more filings than Yoda will ever see.
          - New dependency to pin; its Item text must be mapped back to
            Yoda's character offsets (or the chunker split per Item);
            wrapper filings are likely still a problem. Check first that
            it can parse Yoda's cached HTML offline, and its licence.
       c. Use the filing's own table-of-contents links (most modern
          filings link each TOC entry to an anchor in the body).
          + Exact positions, chosen by the filer, including JPM's
            cross-reference index.
          - Most code: must work on the HTML before cleaning and map
            anchors to clean-text offsets; some filings have no links, so
            a or b is still needed as a fallback.
       In all three: when no reliable heading is found, label the text
       "Other". A missing label is shown as missing; a wrong one misleads.
   R3. Read the annual report a 10-K incorporates by reference (EX-13),
       ONLY for 10-Ks that have one. (Context for the implementer.)
       - Evidence: USB 10-K acc 0000036104-26-000011 (filed 2026-02-23).
         Index lists Seq 1 "10-K" usb-20251231.htm (wrapper, ~138K clean
         chars: Items cite "pages X of the 2025 Annual Report ...
         incorporated herein by reference") and Seq 6 "EX-13"
         usb-20251231_d2.htm (the annual report: MD&A, Risk Factors,
         financial statements). Yoda reads only Seq 1 today.
       - Scope: mostly banks (USB; likely WFC and others). Most 10-Ks have
         no EX-13, so the rule is conditional, not "read both always".
       - Process: in yoda/ingest/edgar.py _download_report(), a 10-K
         currently goes through _get_main_document() (which already fetches
         the index page). Instead read the index once with
         _index_documents(); if any row has doc_type "EX-13" (also accept
         "EX-13.1" etc.: startswith("EX-13")) and a readable .htm/.html/.txt
         name, download Seq 1 + the EX-13 doc(s) and join them exactly as
         the 40-F path does (f"<h1>{doc_type}</h1>\n{html}", URL = main
         doc's). No EX-13 -> Seq 1 only, same as now. No extra HTTP request
         for 10-Ks without EX-13 (the index fetch already happens).
         Generalise _select_main_and_exhibit_99 to take the exhibit prefix
         per form (40-F -> "EX-99", 10-K -> "EX-13"); 10-Q unchanged.
       - Tests (offline, tests/test_recency.py style): a fake index with
         EX-13 -> both docs read, joined, URL = main; without EX-13 -> one
         download only.
       - Size: USB 10-K + EX-13 + 10-Q estimated ~1.3M chars, under the 2M
         limit; the size rule (baseline.full_filing_text) still applies.
       - Known limits: EX-13 is annual-report format without "Item N"
         headings, so section labels will be poor until R2; wrapper Items
         cite page numbers that won't match the clean text.
       - Old caches: a cached USB 10-K (wrapper only) has the same
         accession, so fetch_filings would reuse it. Delete
         data/filings/<ticker>/ for affected tickers once after shipping,
         or include a version marker in latest.json.
       + Restores MD&A, Risk Factors and financial statements for these
         filers. - Larger filings; page references don't resolve.

   XOM (found in the same check; FIXED in edgar.py, automatically): ticker
   XOM now maps to CIK 2115436 (ExxonMobil Holdings Corp, holding-company
   reorganisation, July 2026). Its last 10-K (2026-02-18) is filed only
   under the predecessor CIK 34088 (Exxon Mobil Corp, no ticker now), so
   Yoda found only the 10-Q. SEC submissions JSON has no predecessor field.
   edgar.py section "Predecessor companies" now finds the old company
   itself, only when a ticker has no annual report in 13 months AND filed
   an 8-K12B/8-K12G3: candidates from 10-Q co-filers (index-headers),
   EDGAR name lookup (efts keysTyped) and full-text address search of
   recent 10-K/20-F/40-F; accepted only if exactly one has no ticker, an
   annual report in 13 months, the same SIC code, and a joint filing /
   same phone / same street. Links are saved in
   data/filings/predecessors.json (keyed by ticker, valid only while the
   ticker's CIK matches new_cik). Live-checked on XOM, CLBK, XPRO, DMRC.
   Note: the efts keysTyped endpoint is what EDGAR's search box uses, not
   a documented API; if it changes, the whole search fails visibly (data
   gap "Predecessor search failed: ...") and the report is as it was
   before this feature (no annual report read).
   R4. Only then, if R5 shows weak recall: improve chunks, not by semantic
       chunking. Today's chunker already splits at paragraph breaks
       (1,500 characters, 200 overlap), which is what recursive splitting
       does. Instead:
       a. Prefix each chunk's embedded text with where it came from
          ("JPM 10-K 2025 · MD&A · Net interest income").
          + Cheap; helps queries that name a topic the chunk text doesn't
            repeat. - Needs correct labels (R2); all chunks re-embedded
            once (a few cents per ticker).
       b. Keep financial tables in one chunk with their header row.
          + A number is retrieved with its column and period.
          - Long tables need their own split rule.
       Semantic chunking is not recommended: an extra embedding pass at
       ingest, uneven chunk sizes, and no evidence it beats paragraph
       splits on filings.
   R5. Measure retrieval before changing it: ~40 question -> expected
       passage pairs over 4-5 filings, scored by whether the passage is in
       the top 3 (embeddings only, cents per run).
       + The only way to know whether R4 or R6 helps. - Writing the pairs
       takes time; a small set can mislead.
   R6. Embedding model: do NOT fine-tune now. As far as known, OpenAI does
       not offer fine-tuning for embedding models, so this would mean
       hosting an open model and building thousands of training pairs.
       If R5 shows weak recall, try in this order: hybrid search (keyword
       BM25 + vectors; exact terms like "CET1" or a line-item name match
       better), a reranker over the top ~20, a larger or finance-tuned
       hosted embedding model (check current options and prices first).
       + Each is a smaller step than fine-tuning and measurable with R5.
       - Each adds an API cost or a dependency.
