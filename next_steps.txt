4. Architecture comparison: staged pipeline vs lead analyst method vs
   baseline option B (NOT RUN YET: the smoke and full runs each need an
   explicit yes and enough credit)
   The personality panel was removed (2026-10-30). Two candidate
   architectures are built and run with the baseline on the full
   20-ticker set; the better one becomes Yoda.
   - Staged pipeline: code builds the facts; fixed stages (a filing
     extractor, a post-filing extractor for the 8-K and the call, two
     news/peer researchers, expectations computed in code) feed one
     writer; every claim is checked against the passages it cites, then
     one repair pass.
   - Lead analyst method: a lead picks 4-6 company-specific questions and
     briefs one worker per question; the lead reviews the findings, fills
     gaps once and writes; the same claim check follows. Decided
     2026-10-31: workers read the full shared sources from the one cache
     (no passage search); a follow-up goes back to the same worker; each
     worker may make 4 tool calls, 2 more on a follow-up.
   - Models (decided 2026-10-30): writer Sonnet 5.5 (also the lead in the
     lead analyst method); staged pipeline researchers Haiku 5.5; lead
     analyst workers Sonnet 5.5; claim check Haiku 5.5, with a Sonnet 5.5
     second opinion on the claims Haiku fails (a claim is removed only
     when both agree).
   - Built and shared by every arm (2026-10-30; were 4a and 4b): the evidence store
     (yoda/evidence_store.py, passage IDs), the XBRL fact sheet
     (yoda/ingest/xbrl.py), the report schema and citation checks
     (yoda/schema.py, yoda/report/), and the shared sources fetched once
     per ticker (yoda/sources.py: SharedSources, base_store(), one length
     limit SOURCE_CHARS_LIMIT). Each arm starts its store with
     sources.base_store() and adds its own news, articles and peers.
     Known gaps: banks and oil majors tag no OperatingIncomeLoss or
     LongTermDebt (shown missing); IFRS filers (20-F/40-F) have no us-gaap
     facts, so their fact sheet is all missing.
   - Complexity labels (was 4c; fixed before any report, yoda/eval/complexity.py,
     pinned by tests/test_complexity.py; must not change now):
     * Complex (9): JPM, USB, UNH, XOM, KO, AMZN, JNJ, DIS, BA.
     * Simple (11): AAPL, MSFT, NVDA, AMD, HD, SLB, PG, NFLX, CAT, PANW,
       CRM.
     * Analysis: report the staged pipeline vs lead analyst score gap
       within each group next to the overall gap. With 9-11 tickers per
       group, read group differences as a direction, not proof.
   - Prompt-caching rules for the two candidate methods (item 12): the
     shared source is the first system block, marked as a cache
     breakpoint, role instructions after it; all of an arm's
     source-reading calls share
     model, pinned effort and a sorted tool list; nothing variable (dates,
     IDs) before the breakpoint; warm the cache with one call before
     fanning out parallel calls; 5-minute cache (the staged pipeline uses
     1-hour, decided 2026-10-30: its repair pass starts over 5 minutes
     after the writer's read); no cross-arm sharing;
     prove it with yoda/prompt_cache.cache_misses(). The baseline has no
     breakpoint: it makes one call, so nothing would read the cache.

9. Improve Retrieval Quality
   R1 (section test set), R2 (section detection from the filing's own
   table-of-contents links) and R3 (reading a 10-K's EX-13 annual report)
   are DONE (2026-10-30): tests/test_sections.py, yoda/ingest/chunker.py,
   edgar._EXHIBITS_READ_WITH.
   - Known gap from R2: WFC-style annual reports (EX-13 with no linked
     table of contents, MD&A called "Financial Review") are mislabelled
     (23% accurate); no eval ticker has this form. Fixing it means
     WFC-specific rules, then fresh hold-outs to check they generalise.
     Minor: SU's MD&A after its risk factors is labelled Other; USB's
     EX-13 "Company Information" is not recognised.
   WHEN for the rest: AFTER, and only if wanted. The lead analyst
   method's workers read the full sources (decided 2026-10-31), so R5
   would cover only peer lookups, and R4/R6 only if R5 shows weak
   recall. Note: tools.retrieve_filing and the vector store still return
   chunker windows without passage IDs; an arm that retrieves must return
   store passages, the unit every citation is checked against.
   R4. Improve chunks, not by semantic chunking (today's chunker already
       splits at paragraph breaks):
       a. Prefix each chunk's embedded text with where it came from
          ("JPM 10-K 2025 · MD&A · Net interest income"). Cheap; all
          chunks re-embedded once (a few cents per ticker).
       b. Keep financial tables in one chunk with their header row, so a
          number is retrieved with its column and period. Long tables
          need their own split rule.
   R5. Measure retrieval before changing it: ~40 question -> expected
       passage pairs over 4-5 filings, scored by whether the passage is in
       the top 3 (embeddings only, cents per run). The only way to know
       whether R4 or R6 helps; a small set can mislead.
   R6. Embedding model: do NOT fine-tune (OpenAI offers no embedding
       fine-tuning; it would mean hosting a model and building training
       pairs). If R5 shows weak recall, try in this order: hybrid search
       (BM25 + vectors; exact terms like "CET1" match better), a reranker
       over the top ~20, a larger or finance-tuned hosted embedding model
       (check current options and prices first). Each adds a cost or a
       dependency and is measurable with R5.
   Note on the predecessor lookup (edgar.py, "Predecessor companies"): it
   uses EDGAR's search box endpoint (efts keysTyped), which is not a
   documented API; when it fails, the report says so in its data gaps
   and no annual report is read for that company.
