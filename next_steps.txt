4. Architecture comparison: staged pipeline vs lead analyst method vs
   baseline option B
   Two candidate architectures run with the baseline on the full 20-ticker
   set; the better one becomes Yoda.
   - Staged pipeline (yoda/modes/pipeline.py): code builds the facts;
     fixed stages (a filing extractor, a post-filing extractor for the 8-K
     and the call, two news/peer researchers, expectations computed in
     code) feed one writer; every claim is checked against the passages it
     cites, then one repair pass.
   - Lead analyst method (yoda/modes/lead.py): a lead picks 4-6
     company-specific questions and briefs one worker per question; the
     lead reviews the findings, asks one round of follow-ups (back to the
     same worker) and writes; the same claim check follows. Workers read
     the full shared sources and may make 4 tool calls, 2 more on a
     follow-up.
   - Models: writer Sonnet 5.5 (also the lead); staged pipeline
     researchers Haiku 5.5; lead analyst workers Sonnet 5.5; claim check
     Haiku 5.5, with a Sonnet 5.5 second opinion on the claims Haiku fails
     (a claim is removed only when both agree).

     report schema and citation checks, and the shared sources fetched

9. Improve Retrieval Quality
   WHEN: AFTER, and only if wanted. Neither candidate method searches the
   company's own filings (both read the full sources), so retrieval only
   serves competitors' filings (lookup_peer). Note: tools.retrieve_filing
   and the vector store return chunker windows without passage IDs; an arm
   that retrieves must return store passages, the unit every citation is
   checked against.
   - Known gap in section detection: WFC-style annual reports (EX-13 with
     no linked table of contents, MD&A called "Financial Review") are
     mislabelled (23% accurate); no eval ticker has this form. Fixing it
     means WFC-specific rules, then fresh hold-outs to check they
     generalise. Minor: SU's MD&A after its risk factors is labelled Other;
     USB's EX-13 "Company Information" is not recognised.
   R4. Improve chunks, not by semantic chunking (today's chunker already
       splits at paragraph breaks):
       a. Prefix each chunk's embedded text with where it came from
          ("JPM 10-K 2025 · MD&A · Net interest income"). Cheap; all
          chunks re-embedded once (a few cents per ticker).
       b. Keep financial tables in one chunk with their header row, so a
          number is retrieved with its column and period. Long tables
          need their own split rule.
   R5. Measure retrieval before changing it: ~40 question -> expected
       passage pairs over 4-5 filings, scored by whether the passage is in
       the top 3 (embeddings only, cents per run). The only way to know
       whether R4 or R6 helps; a small set can mislead.
   R6. Embedding model: do NOT fine-tune (OpenAI offers no embedding
       fine-tuning; it would mean hosting a model and building training
       pairs). If R5 shows weak recall, try in this order: hybrid search
       (BM25 + vectors; exact terms like "CET1" match better), a reranker
       over the top ~20, a larger or finance-tuned hosted embedding model
       (check current options and prices first). Each adds a cost or a
       dependency and is measurable with R5.
   - Value (checked 2026-10-31): marginal for now. Retrieval serves only
     lookup_peer, and peer filings backed 7.1% of the staged pipeline's
     and 9.3% of the lead analyst method's claims on the smoke run. After
     the full run, count how much the winning method cites peers; do R5
     first if it leans on them.
   - Clean-up: tools.retrieve_filing (search of the company's own filing)
     is used by neither candidate method, only by the retired panel.
   Note on the predecessor lookup (edgar.py, "Predecessor companies"):
   EDGAR's search box endpoint (efts.sec.gov) is not a documented API and
   can't be made one (SEC documents only data.sec.gov's submissions and
   XBRL APIs and their bulk ZIPs). Since 2026-10-31 the co-filers on the
   new company's 10-Qs are tried first, from SEC's archive and the
   documented submissions API; the search is asked only when they don't
   give exactly one match. XOM's predecessor is found this way.

12. Investigate ways to cut report costs while keeping quality
    Already in place: prompt caching within each arm (rules in item 4),
    the judge on OpenAI Flex with cache hits, the baseline through the
    Batch API, effort pinned on every call, usage logged per stage. Not
    adopted (they trade quality or can't be measured without spend):
    lower effort, more Haiku, less filing text for writers, splitting
    Haiku prompts under 100K tokens, batching the two candidate methods.
    WHEN: AFTER, on the winning architecture.
    - Use the full run's per-stage costs and scores to find where money
      goes; compare candidate changes on a few tickers against those
      scores.
    - Done when: a change lowers the average report cost with no drop in
      the judge's scores beyond run-to-run noise.
    - Built 2026-10-31, first used in the full run (4f): 5-minute cache +
      keep-alive. Writing the shared sources to the 1-hour cache cost 2x
      input (55% of a staged pipeline report, 41% of a lead analyst
      report); the 5-minute cache costs 1.25x, and Anthropic offers no
      lifetime in between. The 1-hour cache was chosen because the repair
      pass starts over 5 minutes after the writer's read; now
      source_calls.keep_cache_alive() re-reads the entry (llm.warm_cache,
      max_tokens=0, billed as a cache read) every 4 minutes for a report's
      whole run. One keep-alive that writes is a miss (logged); two in a
      row stop the keep-alives with a WARNING; a refused one is skipped.
      Dry test on the smoke logs (no API calls): saves $0.30 per
      candidate report (95% CI $0.17-0.43, one-sided p = 0.0018; 9-15% of
      cost), ~$11.50 per full run; projection to the other 15 tickers
      consistent (Welch p = 0.99; leave-one-out prompt-size error 5.5%).
      Risk: a late keep-alive rewrites the cache (~$0.60); the saving is
      gone at ~0.5 late keep-alives per report, which only a real run can
      measure. A test run would cost more than one full run saves, so no
      test run: the full run is the test, and each report's log counts
      its misses (the check is in 4f). Rollback: CACHE_TTL = "1h".
