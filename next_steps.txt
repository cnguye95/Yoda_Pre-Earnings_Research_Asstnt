4. Check the judge: can it see differences, does it agree with a human,
   and are the staged pipeline's claims more trustworthy? (added
   2026-11-02, refined the same day)
   CODE CHANGES and PAID RUNS: plan and approve each step first.
   - Why: the full run found no difference between the staged pipeline
     and the baseline, but "no difference" is only as strong as the
     judge's ability to see one. Two warning signs: ceiling effects
     (sell-side usefulness 4.70-4.95; 15-17 ties of 20 on several
     dimensions), and the claim check finding ~11% of the pipeline's
     first-draft claims unsupported while the unchecked baseline scored
     the same on figure accuracy and traceability. No human has checked
     the judge yet.
   - Three questions, each with its own test:
     Q1 Can the judge see differences at all? (planted errors, step B)
     Q2 Does the judge agree with a careful human? (claim audit, E and F)
     Q3 Does the staged pipeline's claim check make its claims more
        trustworthy than the baseline's? (unsupported-claim rate, F)
   - Ground rules:
     * Write the plan (step A) BEFORE any labelling or judging, and keep
       it in the repo, so no result can be reinterpreted after the fact.
     * The full run's eight-dimension result stays the primary published
       result. New measures are added beside it; nothing replaces it.
     * The judge stays OpenAI gpt-6.1-sol, so the README, the resume and
       any new result keep describing the same judge.
     * Resume consistency (resume goes out before this item is done): the
       resume may only claim what README section 2 says today. If this
       item changes the headline, update the README and the resume
       together.
   - Flaws fixed from the first draft of this item (2026-11-02):
     1. Human labels are per claim, but the judge's scores are per report
        (1-5): they can't be compared directly. Fix: the judge labels the
        SAME claims the human labels (step F), and agreement is measured
        claim by claim.
     2. Tuning the judge on the same human labels used to grade it would
        flatter it. Fix: split the human labels into a calibration set
        (prompt tuning) and a held-out set (the only one reported).
     3. The only rater built the system and may lean towards it. Fix:
        method hidden, evidence IDs and section names removed (method-
        specific ID types like P.* give the method away), claims shuffled
        across methods; re-label a random 30 a week later to measure
        self-consistency; optionally a second person labels 50.
     4. 10 tickers x 15 claims puts too much weight on a few companies.
        Fix: all 20 tickers x 8 claims per method (320 claims), sampled
        evenly across report sections; confidence ranges by resampling
        tickers, not claims.
     5. "Partly supported" was undefined. Fix: two labels plus reason
        codes (step D), a written labelling guide with examples, piloted
        on 20 claims before the real labelling. Labels judge whether the
        cited passages support the claim, not whether it's true in the
        world: a true claim its citations don't back is "not supported".
     6. Adding a rubric dimension changes the judge cache key, so all
        eight existing dimensions would be re-scored and drift by LLM
        noise. Fix: claim checking is a SEPARATE judge pass; the existing
        scores are left untouched.
     7. The audit measures whether claims are supported, not what a
        report left out. Say so; omissions stay with filing_extraction.
     8. "Design the rubric after the human audit" let the instrument fit
        the data. Fix: the judge prompt is tuned on the calibration set
        only (point 2).
   Steps:
   A. Write the plan (free, ~30 min): docs/judge_check_plan.md with the
      three questions, the measures, and decision rules, e.g. "the judge
      is trusted for claim checking if its agreement with the human on
      held-out claims is Cohen's kappa >= 0.6"; "Q3 is answered if the
      95% range of the unsupported-rate gap excludes 0".
   B. Planted-error test, Q1 (design B chosen 2026-11-02; code + paid,
      ~$5 expected, $12.84 worst case; ~15 min; no human time). Written
      before it runs:
      - Copies: all 20 staged pipeline reports from the full run, each
        with errors planted in 10% of its claims (~7 of ~70), the share
        of first-draft claims the claim check flags. About 70% of them
        get one figure changed by +20% (citations kept, so the figure
        no longer matches its source); the rest have their citations
        pointed at an unrelated passage. Every change is listed in
        data/eval/planted/planted_changes.md.
      - Commands: python -m yoda.eval.planted make; then
        python -m yoda.eval.runner --rescore data/eval/planted --modes pipeline --judge-budget 10;
        then python -m yoda.eval.planted compare.
      - Compared with: the originals' scores from the full run
        (data/eval/full/rescore/results.csv); the originals are not
        re-judged. Same statistics as README section 2: the gap per
        ticker (copy minus original) and its 95% bootstrap range.
      - Pass rule: figure_accuracy's 95% range lies entirely below 0.
        source_traceability is reported beside it (a range below 0 means
        the judge also notices wrong citations). Partial: only
        source_traceability drops. Fail: neither does.
      - How the result is used, pass or fail: README section 2 gets a
        short "Planted-error test" subsection explaining what was planted,
        why 10%, the result and what it means for the headline.
        Pass: the tie isn't a blind judge; "matched quality" stands on
        the resume, and a rigor bullet may be added ("Tested the LLM
        judge with planted errors: it penalised wrong figures at the rate
        the claim check removes them"). Fail: a limitation saying the tie
        may reflect a judge that misses wrong figures; the resume says
        "no measurable quality difference" (item 1); E and F come first.
        Either way the planted claims become known-answer cases for F.
      - Judging is a new judge-cache run, so the cache drops batch A's
        cached scores (the full run's older run; its scores stay in
        results.csv). Step C then re-judges batch A's first scores too:
        about $8 more, and still a valid noise measure.
   C. Judge noise (paid, ~$14, ~45 min; no code):
        python -m yoda.eval.runner --rescore data/eval/full --repeat --judge-budget 20 --out data/eval/full/repeat
      How often the judge gives the same report the same score, and so
      the smallest gap it can detect.
   D. Build the audit kit (code, free): a script that samples the 320
      claims as in flaw 4, shows each claim with the full text of the
      passages it cites (IDs and method hidden), shuffles them, writes
      Markdown sheets to label in VS Code, and keeps
      the answer key apart; marks 80 as calibration (20 of them the
      pilot) and 240 as held-out. Plus the labelling guide, with rules
      for rounding, the writer's own arithmetic, inferences labelled as
      estimates, and claims citing several passages. Labels:
        Supported      every number and fact in the claim is in the
                       cited passages
        Not supported  plus one reason: wrong number / not in the cited
                       source / overstated / cites the wrong source
        Not checkable  an opinion or forecast; left out of the scoring
      Agreement (kappa) is measured on Supported vs Not supported; the
      reason codes show what kind of errors each side misses.
   E. Human audit (free, ~6-8 hours, Calis): the
      pilot 20, then refine the guide; then the rest; a week later,
      re-label 30 at random. The same steps for every claim.
   F. Claim-level judge pass, Q2 and Q3 (code + paid, ~$2-4 for all 40
      baseline and staged pipeline reports): one judge call per report
      labels every claim (~70) against its cited passages (~25K-token
      prompt; measured 2026-11-02: 69-71 claims and ~75-88K characters
      of cited text per report). Tune its prompt on the calibration set,
      then report agreement on the held-out set (kappa, confusion
      matrix). If it passes step A's rule, use its labels for all ~2,800
      claims: each method's unsupported-claim rate with a 95% range by
      resampling tickers. Optional: the lead analyst method's 20 reports
      (~$1-2 more).
   G. Publish: a "Judge check" subsection in README section 2 (planted
      errors, noise, human agreement, unsupported-claim rate per method),
      the original verdict next to any new finding; rerun
      docs/charts/make_charts.py if any chart's numbers change; update the
      limitations; update resume bullets only if the headline changed.
   - Not doing (decided 2026-11-02): pairwise judging, a second judge
     from another model family, and sharper rubric anchors. Each would
     re-judge all 60 reports (no new reports, but ~$14+ per pass) and
     add a second headline to explain.
   - What the human audit improves: the claim-level judge pass (F), not
     the eight-dimension rubric judge behind the headline. The planted-
     error test (B) is the only step that tests the headline's scores.
   - Order and timing: B first, before the resume goes out (approved
     2026-11-02), because a failed B changes the resume wording (item
